# missingarr 0.10.1: Korrekturen aus dem Debug-Bericht Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** missingarr 0.10.1 behebt die Befunde B1, B2, B4, B6, B7, B8, B9, B10 und B12 aus dem Debug-Bericht zu 0.10.0 vom 03.10.2026, ohne neue Einstellung und ohne neue Spalte.

**Architecture:** Neun kleine Korrekturen, jede ein Task mit eigenen Tests, dazu ein Release-Task. Die Fehlend-Suche ändert sich an ihrer einen Auswahlstelle `SearchMissingSkill._take_eligible()` (B1, B6) und an ihren Texten (B1, B4); Sonarr liest die Wanted- und Cutoff-Listen mit `includeSeries=true` statt jedes Mal die ganze Serienliste (B10, Voraussetzung für die Anime-Erkennung in B6). Zeitstempel schreibt jede INSERT-Anweisung ausdrücklich in Ortszeit, und `init_db()` rechnet alte UTC-Zeilen einmal um (B2). Der Agent plant seinen ersten Lauf ab dem letzten Start aus der Historie und füllt die Karte aus der Historie (B7), der Ruhezeit-Status kommt aus der Uhr (B8). Die geprüfte Suche hält bei „no approved release“ Anzahl und Ablehnungsgründe in der vorhandenen Spalte `error_message` fest (B9), der Imports-Zähler bekommt einen eigenen Cache von 50 Sekunden (B12).

**Tech Stack:** Python 3.12, FastAPI mit Jinja2, SQLite, APScheduler 3, `pytest`; Node für die vorhandenen Tests der Seiten-Komponenten. Keine neue Abhängigkeit.

## Entscheidungen

Innerhalb der festen Vorgaben offen gelassen, so festgelegt:

1. **B1 „vorhanden“** heißt: das Feld hat einen Wert, der nicht leer ist (`any(record.get(name) for name in RADARR_DATES)`); `null` und `""` zählen als fehlend. Die Info-Zeile ist die bestehende Zusammenfassung des Laufs, auf Stufe `info` statt `debug`, sobald `skipped_unavailable > 0` ist und es Kandidaten gibt. Ist nichts zu suchen, bleibt es bei der einen Info-Zeile „Nothing to search — …“ (keine zweite Zeile mit denselben Zahlen). Keine Notiz in der Historie, wie in 0.10.0.
2. **B2 Spalten:** `activity_log.created_at` (`db/activity.py`), `searched_items.searched_at` (beide INSERT-Wege: `history._UPSERT_SEARCHED` und `searched.add`) und `instances.created_at`/`updated_at` (`create` und die drei UPDATE-Anweisungen). `search_history`, `search_history_items`, `checked_search_log` und `checked_search_pauses` schreiben ihre Zeiten schon ausdrücklich in Ortszeit.
3. **B2 Umrechnung:** Erkennung über das gespeicherte `CREATE TABLE` in `sqlite_master`, ohne Leerraum: enthält es `(datetime('now'))`, ist der Standardwert noch UTC. `activity_log`: jede Zeile kam über den Standardwert, also wird jede Zeile mit `datetime(created_at, 'localtime')` umgerechnet (die Sommer-/Winterzeit der jeweiligen Zeile gilt). `searched_items` ist gemischt: eine neue Zeile kam über den Standardwert (UTC), eine wiederholte Suche schrieb Ortszeit; beides ist an der Zeile nicht zu unterscheiden. Eine Zeile, deren Schreiber bekannt ist (`history_item_id`, seit 0.9.0; der Eintrag in `search_history_items` existiert noch und hat `created_at`), bekommt dessen `created_at` (Ortszeit, in derselben Transaktion geschrieben). Andere Zeilen (vor 0.9.0 oder Historie geleert) bleiben, wie sie sind: sie werden höchstens einmal um den UTC-Abstand zu früh frei. `instances` wird nicht umgerechnet: die Zeiten werden nirgends gezeigt oder verglichen, und `updated_at` war auf jeder Datenbank UTC, auch auf neuen. Die Markierung `local_timestamps_since` (Ortszeit des ersten Starts von 0.10.1) wird in derselben Transaktion wie die Umrechnung geschrieben, auf neuen Datenbanken ohne Umrechnung. Live ist der Cache leer; umgerechnet werden dort nur die Log-Zeilen.
4. **B4:** Der Hinweis auf „Reset dry run“ steht nur im Testlauf und nur, wenn mindestens ein Titel schon in dieser Runde geprüft war (`skipped_cache > 0`); ist die Wanted-Liste leer, wäre der Hinweis falsch. „title(s)“ gilt im Testlauf auch für „All N title(s) failed“; Active und Suchbefehl behalten „submission(s)“. Die Seite Searched bekommt die IDs der Instanzen im Testlauf als JSON-Konstante; die `@click`-Attribute bleiben unverändert (ein bestehender Test prüft sie wörtlich). „Reset All“ nennt den Testlauf, wenn mindestens eine Instanz im Testlauf ist. Die Upgrade-Suche hat keinen Text „already searched“ und bleibt unverändert.
5. **B10:** `includeSeries=true` nur für Sonarr, auf jedem Lesen von wanted/missing (auch der Probe der zufälligen Reihenfolge, damit es eine Stelle gibt: `_wanted_params`). Radarr fragt wie bisher. Ohne Serienliste hätte die Upgrade-Suche bei Sonarr kein Profil mehr (Cache-Einträge würden nach einer Profiländerung nie frei); deshalb liest auch die Cutoff-Liste ihre Seiten mit `includeSeries=true`, und der Upgrade-Eintrag übernimmt `qualityProfileId` der eingebetteten Serie (die Probe mit `pageSize` 1 nicht). `GET /api/v3/series` fällt ganz weg; für Datensätze ohne eingebettete Serie bleibt der Rückfall `series_loader` (`GET /api/v3/series/{id}` nur für gesuchte Titel), wie bisher nach einem Fehler beim Lesen der Liste. Beide Skills lesen die Profile erst nach der Prüfung auf Indexer-Pause.
6. **B6:** „Höchstens eine Folge einer Anime-Serie je Lauf“ heißt eine Anime-Folge insgesamt je Lauf, nicht eine je Anime-Serie (Ziel ist die Last auf Sonarr und den Indexern). Gezählt wird über alle Seiten eines Laufs (`_Stats`). Erkannt wird `series.seriesType == "anime"` der eingebetteten Serie (Task 4); ein Datensatz ohne Serie zählt als normale Folge. Die Bedingung steht nach Warteschlange und Fehlerpause: eine Anime-Folge, die dort ausgelassen wird, verbraucht den Platz nicht. Die Zusammenfassung nennt die wartenden Folgen („N more anime episode(s) wait for a later run“). Mit dem Suchbefehl geht die eine Anime-Folge in jedem `missing_mode` als `EpisodeSearch` hinaus und wird je Folge dedupliziert: Season Packs, Smart und Show Batch würden sonst eine `SeasonSearch` oder `SeriesSearch` schicken, und Sonarr sucht eine Anime-Staffel Folge für Folge (jede ausgestrahlte überwachte), was die Grenze aushebeln würde (Codex-Runde 1). Andere Serien behalten ihren Modus. „Jeder Sammelweg“ heißt wie im Plan zu 0.10.0 die Wege der Fehlend-Suche (`_collect_random`, `_collect_ordered`, beide über `_take_eligible`). Die Upgrade-Suche bleibt unverändert: der Bericht belegt die Last nur für die Fehlend-Suche, und Upgrades laufen mit einem Viertel der Häufigkeit und standardmäßig einem Titel je Lauf.
7. **B7:** Je Skill: die Fehlend-Suche ab ihrem letzten Start mit dem Intervall, die Upgrade-Suche ab ihrem letzten Start mit dem vierfachen Intervall. „Letzter Start“ ist `MAX(started_at)` aller Läufe des Skills, auch Force-Läufe und Fehlerläufe. Ohne früheren Lauf (neue Instanz, Historie geleert) oder wenn die Historie nicht lesbar ist, gilt wie bisher ein Intervall ab jetzt. Die Karte: `last_wanted`, `last_triggered` und `last_verified` aus dem neuesten fertigen Lauf (eine Zeile, wie `get_latest_run_verification`, B-L4), `last_sync` aus dem neuesten fertigen Lauf, der weder Fehler noch Pause war (Pause erkannt am Text „Checked search paused“ in `error_message`), auf Minuten gekürzt wie in `finish_search_run`. Das geschieht in `_run()` vor dem Start des Schedulers; ein Fehler beim Lesen schreibt nur eine Warnung ins Container-Log.
8. **B8:** `display_status()` leitet nur „scheduled“ und „quiet“ aus der Uhr ab; „running“, „starting“, „off“ und „error“ bleiben. Ein wegen der Ruhezeit übersprungener Lauf setzt „quiet“ nicht über „running“: ein Force-Lauf, der in die Ruhezeit hineinläuft, bleibt auf der Karte RUNNING, auch wenn der Scheduler währenddessen einen Lauf überspringt (Codex-Runde 2). Die Info-Zeile gilt je Agent und Fenster: Jeder Job außerhalb der Ruhezeit (der Health-Check alle 5 Minuten) setzt die Markierung zurück. Wird eine Instanz in der Ruhezeit gespeichert, schreibt der neue Agent die Zeile noch einmal; hingenommen. Weitere Sprünge im selben Fenster bleiben Debug-Zeilen.
9. **B9 Speicher:** die vorhandene Spalte `checked_search_log.error_message` der Zeile mit dem Ergebnis `no_results`, keine Schemaänderung. Text: „N release(s) returned, none approved — most frequent rejections: A (n); B (n); C (n)“, ohne Gründe nur der erste Teil, bei leerer Antwort „no release returned“. Ein Grund zählt je Release einmal; bei Gleichstand gilt die Reihenfolge des ersten Auftretens. `rejections` darf Texte oder Objekte mit `reason` enthalten. Der Wert in der Datenbank bleibt `no_results` (Filter, CSV, Zähler, API und die Freigabe nach „Search again if still missing“ unverändert); nur die Beschriftung ändert sich (Abzeichen, Filter, Zählertabelle). Die Seite zeigt den Text als Tooltip des Abzeichens und in der aufgeklappten Zeile, die CSV in der Spalte „reasons“. Zeilen mit Indexer-Ausfall bleiben Fehler mit ihrem Text.
10. **B12:** eigene Konstante `COUNT_CACHE_SECONDS = 50` nur für `cached_count()`; Vorschläge, Warteschlangen-Abbild und Serien behalten `CACHE_SECONDS = 60`. Die Seite fragt weiter alle 60 s (`app.js` unverändert).
11. **Doku:** `CHANGELOG.md` bekommt `## [0.10.1] - 2026-10-03` mit `### Fixed` (B1, B2, B7, B8, B4) und `### Changed` (B6, B9, B10, B12); der Abschnitt 0.10.0 bleibt unverändert. README: Zeilen zu Interval, Quiet, Hours After Release, Missing Per Run, „no results“ → „no approved release“, Runden des Testlaufs, Zähler, und ein Abschnitt „Upgrading to 0.10.1“. Tooltips: `hours_after_release`, `missing_per_run`, `cs_search_again_after_days`. Hilfe: Ruhezeit und Testlauf. def _utc_default(conn: sqlite3.Connection, table: str) -> bool:
    """Does the stored CREATE TABLE of `table` still carry the column
    default datetime('now') (UTC) of databases created before 25.03.2026?
    CREATE TABLE IF NOT EXISTS never changed it on such databases."""
    row = conn.execute("SELECT sql FROM sqlite_master WHERE type='table' AND name=?", (table,)).fetchone()
    return bool(row) and "(datetime('now'))" in "".join(row[0].split())


def _convert_utc_timestamps(conn: sqlite3.Connection) -> None:
    """Once per database (marker LOCAL_TIMESTAMPS_SETTING, same transaction):
    timestamps written through the old UTC column default become local time.

    activity_log: every row got its created_at from the default, so on an
    old database every row is UTC. searched_items: a new row took searched_at
    from the default (UTC), a repeated search wrote local time, so the rows
    are mixed. A row whose writer is known (history_item_id, since 0.9.0)
    takes the created_at of that history item (local time, written in the
    same transaction); other rows stay as they are. Since 0.10.1 every
    INSERT writes these columns explicitly in local time. A database created
    with the local default is never converted, only marked."""
    if conn.execute("SELECT 1 FROM app_settings WHERE key=?", (LOCAL_TIMESTAMPS_SETTING,)).fetchone():
        return
    if _utc_default(conn, "activity_log"):
        conn.execute("UPDATE activity_log SET created_at = datetime(created_at, 'localtime')")
    if _utc_default(conn, "searched_items"):
        conn.execute(
            "UPDATE searched_items SET searched_at = ("
            "  SELECT si.created_at FROM search_history_items si WHERE si.id = searched_items.history_item_id) "
            "WHERE EXISTS (SELECT 1 FROM search_history_items si "
            "              WHERE si.id = searched_items.history_item_id AND si.created_at IS NOT NULL)"
        )
    conn.execute(
        "INSERT INTO app_settings (key, value) VALUES (?, datetime('now','localtime'))",
        (LOCAL_TIMESTAMPS_SETTING,),
    )
